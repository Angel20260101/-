# 靜態網站收單系統：設計指南與踩坑筆記

> 來源：心情AED 落地頁專案（2026-09/10）。該專案最終功能完整，但過程中約有七成時間花在
> 可避免的繞路。這份筆記的目的是讓下一次直接跳到正確答案。

---

## 一、先看這張表就好

你要做的是「**靜態網頁 + 表單收單 + 自動寄信**」，可行方案依**可靠性**排序：

| 方案 | 可靠性 | 畫面自由度 | 何時選它 |
|---|---|---|---|
| **自訂表單 → `formResponse`** | ★★★★★ | 完全自訂 | **預設選這個** |
| 嵌入 Google 表單 iframe | ★★★★☆ | 低（Google 樣式） | 趕時間、不在意外觀 |
| 按鈕導向 Google 表單 | ★★★★★ | 中（離站） | 訪客可以接受離開頁面 |
| 自訂表單 → Apps Script `/exec` | ★☆☆☆☆ | 完全自訂 | **不要用**（見第三節） |
| 自訂表單 → Sheets API v4 | ★★★★☆ | 完全自訂 | 需要自架後端藏金鑰時 |

**結論：第一列同時滿足「完全自訂畫面」和「高可靠性」，沒有理由選別的。**

## 二、推薦架構（可直接複製）

```
訪客在自己的落地頁填表
      │ 原生 form POST（target 指向隱藏 iframe，頁面不跳走）
      ▼
https://docs.google.com/forms/d/e/<FORM_ID>/formResponse
      │
      ▼
Google 表單的回覆試算表
      │ onFormSubmit 觸發器（在 Google 伺服器端執行）
      ├──► 寄確認信給填單者
      └──► 寄通知信給擁有者
```

### 為什麼這個組合會贏

1. **送出是「瀏覽器原生表單送出」**，不是 JavaScript 發起的跨域請求 —— 不受追蹤防護管轄
2. **寄信在伺服器端**，訪客送出後立刻關機也照寄，瀏覽器不在關鍵路徑上
3. **畫面 100% 自己的**，訪客不會看到任何第三方介面

### 關鍵實作細節

```html
<form method="POST" target="sink"
      action="https://docs.google.com/forms/d/e/<FORM_ID>/formResponse">
  <input name="entry.1234567890" required>          <!-- 編號用 getEntryIds() 取得 -->
  <input type="email" name="entry.2345678901" required>
  <input type="hidden" name="emailAddress" value="">  <!-- 開了「收集信箱」才需要 -->
  <button type="submit">送出</button>
</form>
<iframe name="sink" style="display:none"></iframe>
```

JS 只做三件事：送出前把信箱同步到 `emailAddress`、監聽 iframe 的 `load` 顯示成功訊息、
設一個 15 秒逾時避免卡在「送出中」。**不要用 JS 攔截送出改成 fetch。**

取得 `entry.NNN` 編號的兩種方法：
- Google 表單 → ⋮ → **取得預先填入的連結** → 隨便填 → 取得連結 → 網址裡就有
- Apps Script：`form.createResponse()` 填假值 → `toPrefilledUrl()` → 解析 `entry.`

## 三、絕對不要做的事

### 🚫 不要讓前端 JavaScript 跨網域 POST 到 Apps Script 的 `/exec`

這是本專案最大的時間黑洞。在 iOS Safari 上**四種送出方式全部失敗**：

| 方式 | 結果 |
|---|---|
| `fetch()` POST | `TypeError: Load failed` |
| 隱藏 iframe + 表單 POST | `load` 事件觸發，但請求沒送達 |
| JSONP（`<script src>`） | 被擋 |
| 整頁導向 | Google 回錯誤頁 |

而**同一支手機，直接在網址列開同一個 `/exec` 卻完全正常**。

> **判斷原則：「我能手動開這個網址」不等於「我的網頁能對它發請求」。** 這是兩種
> 完全不同的瀏覽器行為，受不同的安全政策管轄。

### 🚫 不要在讀不到回應時假設成功

最難查的 bug。`mode: 'no-cors'` 的 fetch 讀不到回應，當時的程式碼在請求「送得出去」
時就顯示「確認信已寄到您的信箱」——**實際上一筆都沒寫進去**。

畫面綠燈、後台全空，導致後續好幾輪偵錯建立在錯誤的事實上。

```js
// ❌ 錯
fetch(url, {mode:'no-cors'}).then(() => showSuccess('確認信已寄出'));

// ✅ 對
fetch(url, {mode:'no-cors'})
  .then(() => showSuccess('已送出您的資料'))   // 只說送出，不承諾結果
  .catch(() => showError('送出失敗'));
```

### 🚫 不要讓「靜默略過」跟「成功」長得一樣

蜜罐（honeypot）命中時回傳 `{ok:true}`，跟真正成功完全無法分辨。真人被瀏覽器自動填入
誤判成機器人時，從外部看不出任何異狀。

```js
// ✅ 回傳可分辨的結果
if (p['bot-field']) return {ok:true, skipped:'honeypot', got:p['bot-field']};
```

同理，寄信失敗被 `try/catch` 吞掉只寫 console，回傳仍是乾淨的 `ok:true` —— 要把
`mailSent: false, mailError: '...'` 一併回傳。

### 🚫 不要把自動播放影片放在首屏

本專案前身曾在約 20 人同時進站時整群卡住。原因三件事疊加：

1. 影片 `moov` atom 在檔尾（沒開 faststart）→ **必須下載完整支才能播第一格**
2. `cache-control: private, max-age=0` → 完全不快取，每人每次重抓
3. 彈窗 autoplay 且沒有逾時保險絲 → 卡住時沒有脫身機制

20 人 × 26 MB = 一瞬間 520 MB。修完後每人 0.34 MB。

## 四、開工前檢查清單

### 架構選型

- [ ] 送出路徑上有沒有「從我的網域對別人的網域發 JS 請求」？有的話先想替代方案
- [ ] 寄信／寫入資料是在伺服器端還是瀏覽器端觸發？瀏覽器端 = 單點故障
- [ ] 這個方案在「使用者關掉分頁」「網路中斷」「開無痕」時會怎樣？
- [ ] 有沒有不需要跨域就能達成的做法？（通常有，而且比較好）

### 第三方服務

- [ ] 要串的服務有沒有「官方支援從靜態頁送資料」的端點？優先用它
- [ ] 需要 API 金鑰的方案 → **金鑰絕不能放前端**，那代表你需要後端，成本要算進去
- [ ] 有沒有免費額度上限？（Gmail 經 Apps Script：一般帳號 100 封/日，Workspace 1500）

### 可觀測性（最容易忽略，但省時間最多）

- [ ] 失敗時前端看得到真正的原因嗎？還是只有一句「發生錯誤」？
- [ ] 後端每個提早 return 的分支，回傳值分得出來嗎？
- [ ] 有沒有一個不用完整走流程就能驗證的自我測試函式？
- [ ] 線上跑的是哪個版本，從外面看得出來嗎？（放一個 `version` 欄位）

## 五、偵錯方法論

### 連續失敗兩次就回頭檢查前提

本專案在「打 Apps Script `/exec`」這個錯誤前提下，連換四種送出方式。
**在錯誤前提下迭代，換再多手法都是白做。**

> 第三次失敗時應該問的不是「還有什麼方法可以送」，而是
> 「**是不是送給錯的對象了？**」

### 一次只改一個變數

曾經同時換了「裝置（桌機→手機）」和「參數（簡單→複雜）」，結果失敗了也不知道是哪個
造成的，又多花一輪。

### 優先取得「能二分」的證據

| 證據 | 能分辨什麼 |
|---|---|
| 後台有沒有新資料 | 請求有沒有真的到達伺服器 |
| 伺服器執行紀錄 | 程式有沒有被呼叫、錯在哪一行 |
| 瀏覽器的實際錯誤文字 | 哪一層擋的 |

**沒有這三者就是在猜。** 本專案多次因為拿不到執行紀錄而反覆猜測。

### 錯誤訊息的措辭會透露環境

- `TypeError: Failed to fetch` → Chrome 系
- `TypeError: Load failed` → **Safari**

本專案就是靠 `Load failed` 這三個字才確認問題出在 iOS Safari 的追蹤防護，
在那之前一直往 CORS 設定的方向鑽。**請使用者原文複製錯誤訊息，不要只說「失敗了」。**

## 六、真機測試清單

**桌機測試通過 ≠ 可以上線。** 本專案所有失敗案例在桌機 Chrome 都是通的。

| 環境 | 必測 | 為什麼 |
|---|---|---|
| iPhone Safari（一般分頁） | ✅ | 追蹤防護規則與桌機完全不同 |
| iPhone Safari（無痕） | ✅ | 限制更嚴，是最壞情況 |
| Android Chrome | ✅ | |
| 行動網路（非 Wi-Fi） | ✅ | 測真實載入速度 |
| 多人同時（至少 5 人） | ✅ | 正式場合前先小規模驗證 |

B2B landing page 的訪客（主管、HR）大多用手機開連結。**只在桌機測過就上線，等於把
坑留給客戶踩 —— 而且他們不會回報，只會默默離開。**

## 七、Google 表單特有的地雷

| 地雷 | 症狀 | 解法 |
|---|---|---|
| 下拉選項文字不一致 | Google 默默拒收該筆，不報錯 | 前端 `<option>` 與表單選項**逐字相同** |
| `FormApp.create()` 不設顯示標題 | 表單頁面沒有抬頭 | 另外呼叫 `form.setTitle()` |
| `form.getItems()` 回傳泛型 Item | `setRequired is not a function` | 先 `asTextItem()` / `asListItem()` 轉型 |
| 「收集電子郵件地址」 | 信箱欄位收不到 | 額外送固定名稱 `emailAddress` |
| 多個 `.gs` 檔同名 `const` | 整個專案跑不動 | **所有 .gs 共用同一全域範圍**，加前綴 |
| 存檔 ≠ 部署 | 改了程式沒生效 | 網頁應用程式要「管理部署作業 → 新版本」 |

## 八、三條最值得記住的原則

1. **可靠性優於美觀，但不要以為兩者只能二選一。**
   本專案一度在「漂亮但送不出去」和「能用但很醜」之間拉扯，最後的答案是兩者兼得 ——
   只是需要先找對送出的端點。遇到這種取捨時，先確認是不是假的取捨。

2. **讀不到回應時，寧可報錯，不要報成功。**
   假陽性比直接失敗更昂貴。失敗至少會被發現，假成功會讓你在錯誤的事實上繼續蓋房子。

3. **別人踩過的坑是訊號，不是雜訊。**
   本專案一開始就被告知「同學也卡在抓不到資料」，當時沒有重視。
   同一個地方多人卡住，通常代表那是方案的固有風險，不是個人操作問題。
