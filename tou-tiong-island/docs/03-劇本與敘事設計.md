# 03｜劇本與敘事設計

## 六篇故事

| # | 故事 | 主題 | 對應島嶼 |
|---|---|---|---|
| 1 | 《晚上九點十七分》 | 工作責任與個人界線（主管下班後傳訊） | 界線島 |
| 2 | 《第四十七通電話》 | 委屈與自我保護（客服面對情緒激動的顧客） | 回聲島 |
| 3 | 《凌晨三點的警示燈》 | 壓力、責任與求援（輪班現場突發狀況） | 夜哨島 |
| 4 | 《那份簡報的名字》 | 公平、人際關係與溝通（工作成果未被看見） | 署名島 |
| 5 | 《年夜飯前的那通電話》 | 關係與自主（親友期待與拒絕） | 歸返島 |
| 6 | 《週日晚上十一點》 | 自我要求與休息焦慮（明明疲累卻無法休息） | 歇腳島 |

**完整劇本在 [`docs/scripts/`](./scripts/)**，每篇包含流程圖、逐節點的完整旁白與對白、
每個選項的立即反應與實際後果、心聲線索、所有分支與匯流、條件式對白、全部固定結局與
結局判定表、三條航線的判定規則，以及重玩可探索的內容。

那些文件由 `npm run docs` 從 `content/stories/*.json` 產生——**JSON 才是唯一的真實來源**，
文件不可能和程式跑的不一樣。

## 每篇的結構

```
開場（旁白）→ 情境建立（旁白）
    ↓
決策點一 ──┬─ 分支 A ─┐
           ├─ 分支 B ─┼─→ 匯流一（條件式對白保留前面的痕跡）
           └─ 分支 C ─┘
    ↓
決策點二 ──┬─ 分支 A ─┐
           ├─ 分支 B ─┼─→ 匯流二
           └─ 分支 C ─┘
    ↓
條件分流（依狀態走向三個不同版本的場景）
    ↓
決策點三 ──┬─ 分支 A ─┐
           ├─ 分支 B ─┼─→ 結局判定（五選一）
           └─ 分支 C ─┘
```

每篇：**26 個節點、3 個決策點、9 個選項、5 個固定結局、3 條航線、27 條可走完的路徑**。
六篇合計 **162 條路徑、30 個結局、18 條航線**。

## 敘事原則

### 重要選擇真正改變劇情，短分支後適度匯流

- 每個選項都有專屬的**立即反應**（不同的對白、不同的後續事件）與專屬的**分支節點**。
- 分支在匯流節點收束，但匯流節點帶**條件式對白**：同一個場景，走不同路線讀到的句子不同。
- 中段還有一次**條件分流**，依累積狀態走向三個版本的場景。
  例如故事一的「星期四早上」分成撐著的、睡飽的、中間的三個版本，怡潔講的話也不一樣。

這樣做的好處：分支數可控（27 條而不是數百條），但重玩時的體感差異很明顯。

### 沒有標準答案

- 選項文案不暗示優劣。「硬做完」和「直接去睡」都有各自的副標，語氣一致。
- 每個結局都有一段 `recap.closing`，說明這個選擇「做對了什麼」與「代價落在哪裡」，
  但不評分、不排序、不說「下次應該」。
- 保底航線（接住／撐住／獨撐／留著／順應／燃燒）的文案特別小心：
  承認這些做法的能力與有效性，只指出成本目前由誰承擔。

### 心聲線索

每個選項配一段**預先編寫**的心聲線索，選完立刻顯示。它做三件事：

1. 把選擇背後的內在機制講出來（為什麼會這樣選，而不是這樣選對不對）。
2. 指出一個當事人通常看不到的角度。
3. 不給建議、不收尾成結論。

心聲線索永遠是寫好的文字，**不由 AI 生成**。AI 回饋是另一段、是選配、在結算的第四格。

### 寫作慣例

- 臺灣繁體中文，口語。對白寫成真的會從嘴巴說出來的樣子。
- 具體細節優先於形容詞：「九點十七分」「十一分二十八秒」「耳朵上方那條壓痕」。
- 配角不是功能，有自己的立場與理由（林經理自己也半夜在回信、子涵被說過太愛講誰誰誰做的）。
- 不用驚嘆號、不用打氣詞、不用「親愛的」。
- 旁白不替玩家決定感受：寫「你的手指停在送出鍵上兩秒」，不寫「你很焦慮」。

### 內容提醒

每篇在 `content_notes` 標示內容性質（職場壓力、言語攻擊、工安風險、家庭關係⋯⋯），
出航前的島嶼面板會顯示，讓玩家自己決定今天要不要走這一篇。

## 資料格式

劇本資料契約在 [`schema/story.schema.json`](../schema/story.schema.json)。
節點必備欄位：`node_id`、`node_type`、`dialogue`、`choices`、`conditions`、
`state_effects`、`next_node_id`、`ending_id`。

```jsonc
{
  "node_id": "n_01_d1",
  "node_type": "decision",          // narration | decision | converge | conditional | ending
  "title": "決策點一：九點十七分的那隻手",
  "scene": { "location": "租屋處", "time": "星期三 21:18", "mood": "手指懸在螢幕上方" },
  "dialogue": [{ "speaker": "narration", "style": "narration", "text": "..." }],
  "conditional_dialogue": [{ "condition": { "tag": "take_on", "op": ">=", "count": 1 },
                             "dialogue": [...] }],
  "choices": [{
    "choice_id": "c_01_d1_tomorrow",
    "text": "回覆：明天早上八點我進公司第一件事處理",
    "hint": "不是拒絕，是把它放回上班時間",
    "immediate": [...],                                  // 立即反應
    "consequence": "你把時間劃回上班時段⋯⋯",              // 實際後果，會在結局回顧列出
    "inner_voice_clue": { "clue_id": "...", "title": "心聲線索", "text": "..." },
    "state_effects": [{ "var": "boundary", "op": "add", "value": 2 }],
    "tags": ["boundary_clear", "speak"],
    "next_node_id": "n_01_b1"
  }]
}
```

條件運算式（`conditions`、`conditional_dialogue`、航線規則共用同一套）：

| 形式 | 意思 |
|---|---|
| `{ "always": true }` | 永遠成立（保底） |
| `{ "all": [...] }` / `{ "any": [...] }` / `{ "not": {...} }` | 邏輯組合 |
| `{ "var": "boundary", "op": ">=", "value": 2 }` | 狀態變數比較 |
| `{ "tag": "speak", "op": ">=", "count": 2 }` | 選項標記的累計次數 |
| `{ "chose": ["c_xxx"] }` | 曾選過其中任一選項 |
| `{ "ending": ["e_01_line"] }` | 目前結局屬於其中之一 |

求值器在 [`src/core/expr.js`](../src/core/expr.js)，前端、驗證器、後端共用同一支。

## 新增第七篇故事要做什麼

1. 寫一份符合 schema 的 JSON，放進 `content/stories/`。
2. 在 `content/practice_cards.json` 加三張卡。
3. 在 `content/island_map.json` 的 `islands[]` 加一座島，含三筆 `growth`。
4. 跑 `npm test` —— 驗證器會檢查連結、孤兒節點、結局與航線可達性、練習卡與地景對應。
5. 跑 `npm run docs` 產生劇本文件。

**不需要修改任何程式碼。**
