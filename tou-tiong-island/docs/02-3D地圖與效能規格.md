# 02｜3D 地圖、互動與手機效能規格

## 視覺方向

Low Poly 低多邊形 ＋ Isometric 等角視角 ＋ 六角形地塊 ＋ **奶油暖調**。
色票集中在 `src/world/palette.js`，3D 與介面共用同一組顏色，所以兩邊不會對不起來。

色調取自 V8 原型：紙白底、淡藍轉蜜桃的天空、暖砂島、鼠尾草綠、金色重點。
**刻意避開偏藍偏冷的粉彩**——療癒感來自暖色與低彩度，不是高明度。

- 平面著色（`flatShading: true`），刻意保留塊面感。
- **完全不使用貼圖**，所有顏色寫在頂點色裡。
- 海面是一塊**有限的圓盤**（大小隨群島算出來），不是無限平面。
  用無限平面會把天空整片擋掉，看不到漸層也看不到太陽——V8 原型的通透感就是這樣來的。
- 每座島一圈淺灘，沒有水面動畫、沒有折射、沒有反射。

### 天空、太陽、雲與天氣：用 CSS 做，不用 draw call

天空漸層、太陽、天氣濛紗都是 canvas **底下**的 CSS 圖層
（`renderer` 開 `alpha: true`、`setClearAlpha(0)` 讓它透出來）。
它們不是 3D 物件，所以增加零個 draw call、零個三角形。

每日天氣打卡會同時改這幾件事（`sceneManager.setWeather()`）：

| | 晴 | 陰 | 雨 |
|---|---|---|---|
| 天空漸層 | 藍天轉蜜桃 | 灰白 | 鉛灰 |
| 太陽（CSS） | 有 | 無 | 無 |
| HemisphereLight 天空／地面色 | 暖黃／暖砂 | 冷灰／灰綠 | 青灰／灰 |
| DirectionalLight 強度 | 1.45 | 0.52 | 0.34 |
| 海水 | 青綠 | 灰青 | 深灰藍 |
| 雲（CSS 天空層） | 2 朵、白 | 全部、淺灰 | 全部、更灰更實 |
| 雨絲 | 0 | 0 | 80 |
| 島民在做的事 | 除草、喝下午茶 | 同晴天 | 換雨衣、撐傘 |

**HemisphereLight 的天空／地面色是最有效的那根槓桿**。在沒有貼圖的平面著色場景裡，
只改方向光強度幾乎看不出差別——晴天和陰天會長得一模一樣。要讓三種天氣一眼分得出來，
得連環境光的色溫一起換。

所有顏色切換都是插值過去的（`_stepColours`），不會硬跳。

**雲為什麼不能做成 3D 物件**：等角視角是往下看的，雲永遠低於相機的視線高度，
所以一定會投影到海面上。不管調成多白、多透明，看起來都像一坨擱淺在水上的東西，
而不是天上的雲。試過拉高、挪到群島外圍、降低不透明度，都救不回來——
這是視角本身的限制，不是參數問題。搬到 CSS 天空層之後它永遠在天空帶裡，
而且 0 個 draw call。

唯一留在 3D 的是打卡用的那一朵：它固定在主島正上方、上面掛著「今天的天氣」標籤，
有島跟標籤當參照，讀得出來是雲。

### 地面細節：拉近才看得到的那一層

鏡頭可以拉到看得見單一棵樹的距離，所以草地與沙灘不能是一整片沒東西的色塊。
除了原本依 `flora` 散佈的樹木，另外有一道**地面細節**（`ground_clutter`），
照 hex 的 `surface` 鋪，所以連 `flora: none` 的空地也有東西看。

| 地表 | 每格數量 | 會長什麼 |
|---|---|---|
| grass | 16 | 三葉草、小灌木、小花、蘑菇、石子、草叢 |
| grass_light | 16 | 三葉草、小灌木、粉花、金花、石子、草叢 |
| grass_dark | 14 | 三葉草、小灌木、蘑菇、石子 |
| sand | 11 | 石子、貝殼、草叢、漂流木 |
| rock | 10 | 石子、三葉草、小灌木 |

`types` 陣列裡重複出現的型別＝出現機率比較高，不用另外寫權重欄位。

三件做錯過、修回來的事：

1. **配色要比地面暗一階才看得見。** 第一版的三葉草用了跟草地同色系同明度的綠，
   鋪了一百多個，畫面上完全看不出差別。細節的對比度比數量重要。
2. **尺寸要克制。** 第一版把石子放大想讓它「看得見」，結果整座島像鋪了碎石；
   漂流木做成 0.36 長，比熊還大。小東西就要小，靠數量鋪質感。
3. **「嘗試次數」要和「目標數量」分開。** 散佈是亂丟點再檢查有沒有撞到別人，
   丟越多越容易被退件。照 `count` 丟 `count` 次，實際只會放到一半
   （設 16 只落了 6 個）。改成最多丟三倍、放滿就停，才真的鋪得滿。

散佈用的是以「島嶼 id ＋ 已解鎖航線數」為種子的亂數，所以每次重建長出來的位置都一樣。

### 會動的東西

島是靜的沒關係，島上不能是死的。所有會動的東西都走 InstancedMesh ＋ 逐幀更新矩陣，
不額外增加 draw call：

| 東西 | 行為 |
|---|---|
| 島民 | `patrol` 來回走（走到底會轉身）、`sip` 喝東西、`breathe` 呼吸起伏、`fish` 釣魚、`circle` 盤旋 |
| 願望島的小船 | 浮在水面上下搖、左右晃，每艘相位不同 |
| 雲 | 橫向漂移，飄出範圍就繞回來 |
| 雨 | 落到水面以下就重新丟回天上 |
| 燈塔光束 | 點燈塔時淡入 0.4 秒、旋轉掃射、淡出 0.6 秒，同時把燈室打亮 |

島民**依天氣換造型與行為**：同一隻熊，晴天是 `animal_bear_mow` 穿吊帶褲在澆花，
雨天換成 `animal_bear_rain` 穿雨衣。換的是模型與行為，不是多畫一次。

### 島民怎麼做才可愛

**不做擬人化。** 沒有站立的人形姿勢、沒有圓柱腿、不讓動物拿工具——
那在低多邊形下只會變成「一顆球插兩根棍子」，鏡頭一拉近就露餡。
牠在做什麼交給旁邊的道具去講（水壺、茶几、釣竿、傘都跟動物合併成同一個模型，
所以還是一個 draw call）。

討喜感的來源很具體，四項缺一不可：

| | 做法 |
|---|---|
| 圓 | 身體用 `ball()`（IcosahedronGeometry detail 1，80 面），不是 `blob()` 的 20 面。20 面的球在拉近時是一顆石頭，不是一隻動物 |
| 眼睛 | **白眼球 → 黑眼珠 → 一點反光**，三層疊上去。單純一顆深色的點會讓動物看起來沒有精神；原本的島民甚至一隻眼睛都沒有 |
| 腮紅 | 兩團淡粉色。這是最便宜也最有效的一項 |
| 衣服與配件 | 一件衣服 ＋ 一個配件：草帽、蝴蝶結、鈴鐺項圈、鴨舌帽、雨衣。配件要避開眼睛——狐狸的帽子第一版壓在眼睛上，整張臉就沒了 |

臉上的東西要用 `onHead()` 貼在頭那顆球的**表面**上。第一版直接寫死 z 座標，
結果整張臉都埋在頭裡面，渲染出來一隻眼睛都看不到。

島民從每隻約 200 個三角形變成約 900 個。三角形在 instancing 之下幾乎免費，
draw call 一個都沒有增加。

## 互動

| 操作 | 手機 | 電腦 |
|---|---|---|
| 旋轉群島 | 單指拖曳 | 滑鼠拖曳 |
| 縮放 | 雙指捏合 | 滾輪 |
| 選島 | 輕點島嶼或它的名牌 | 點擊 |
| 進入島上的功能 | **直接點主島上的文字**（燈塔、碼頭、郵筒） | 同左 |
| 常駐功能 | 右上角直排選單（全景／回島、我的紀錄、登入、關於） | 同左 |

- **島嶼與島上的文字是唯一的點擊互動物件**，沒有角色、沒有移動系統。
- 入口的文字一直看得到，不用先點圓點再點一次——少一次點擊就少一個放棄的理由。
- 點擊用 raycaster 對「隱形代理圓柱」判定（`material.visible = false`，不進渲染但可被射線擊中），
  不對地形或樹木做射線測試。
- 短按且位移小於 8px 才算點選，避免轉動鏡頭時誤觸。
- 島嶼名牌是 DOM 按鈕：比 3D 文字便宜、在小螢幕上清楚、而且螢幕閱讀器讀得到。
- **標籤定位是會點錯的地方，所以規則寫死**：主島的四個入口排成固定的一圈
  （角度 0/90/180/270、半徑隨島的投影大小縮放、夾在 76–128px），位置可預測；
  島名後放，由近到遠依序擺。跑出畫面的標籤直接藏起來
  （`opacity: 0; pointer-events: none`），**不硬擠回邊緣**——擠回來只會疊在一起點錯。
- 右上角的直排選單與左上角的標題卡是**禁區**：標籤撞到就往下讓，不會躲到按鈕後面。
  讓位的方向有先後——預設往上（名牌才不會蓋住島本身），上面是 HUD 就只能往下，
  而且**一旦往下就一路往下**，否則上下來回彈跳會永遠喬不定。
  喬不出位置的標籤直接藏起來：疊在一起會點錯島，比少一個名牌糟糕得多，
  島本身還是點得到。這三條規則都有實測守著（三種螢幕尺寸逐一 `elementFromPoint`）。
- 故事島的名牌前面有橘色序號（`01`–`06`），跟航海圖的編號對得起來。

### 鏡頭

`src/world/cameraController.js` 自己實作，沒有用 OrbitControls：

- 只需要旋轉與縮放，自己寫比較小，也能精準控制觸控行為。
- **刻意不做阻尼**：阻尼會逼著每一幀都重繪，與按需渲染衝突。
- 仰角限制 22°–68°，避免轉到水平看見海平面邊緣或垂直俯視失去立體感。
- 進場停在 `focusHome()`：**把主島與願望島一起框住**。小船從碼頭開出去要看得到它停在哪裡，
  但又不能推太近，否則主島那一圈入口會被擠出畫面。鏡頭中心偏向主島（0.7）。
- 「全覽」用 `fitToWorld()`：把世界 AABB 的角點投到相機座標，直接解出剛好容得下的距離，
  而不是寫死數字——手機直向與桌機橫向需要的距離差很多。
- 直向螢幕（aspect < 0.78）自動把視野角度從 34° 放寬到 46°，否則鏡頭得退到很遠。
- 點主島與願望島**不會推近鏡頭**（它們本來就在預設視角裡）；點故事島才飛過去。
- 「全景」的取景：群島接近正方形，直向手機的水平視角又很窄，所以「把寬度塞進畫面」
  本來就得退得很遠。邊緣每多留 1 單位，鏡頭就要再退好幾單位——原本留 3.2 單位，
  距離被推到 106，島只剩畫面的三分之一。改成留 1.1 之後是 89，島佔畫面寬度約七成。
- 縮放範圍 **6–140**。拉到最近大約看得見單一棵樹、單一朵蘑菇。
  會限制在 6 的是美術而不是效能：再近就會看到低多邊形的稜角。
- **拉近時標籤會淡掉縮小**（距離 10 以內降到 34% 不透明、80% 大小，17 以外恢復）。
  拉近是為了看島上的細節，五個名牌壓在上面最礙事。它們仍然可以點，
  滑過或鍵盤聚焦就恢復全不透明。

## 效能守則

這些不是口號，每一條都在 `src/world/sceneManager.js` 裡被執行：

| 項目 | 做法 |
|---|---|
| 即時陰影 | **關閉**（`renderer.shadowMap.enabled = false`） |
| 動態光源 | **沒有**。只有 1 盞 HemisphereLight ＋ 1 盞不投影的 DirectionalLight，位置固定 |
| 粒子特效 | **沒有** |
| 後製與模糊濾鏡 | **沒有**，不載入任何 EffectComposer |
| 貼圖 | **完全不用**，顏色走頂點色，記憶體與頻寬都省下來 |
| 材質數量 | 整個場景只有 2 個（地形、道具），海面另用最便宜的 MeshBasicMaterial |
| 地形 draw call | 每座島的所有六角地塊合併成 1 個 geometry |
| 道具 draw call | 同型別道具收成 1 個 InstancedMesh，不論島上長出幾百棵樹 |
| 淺灘 | 所有島的淺灘合併成 1 個 geometry |
| 天空・太陽・天氣濛紗 | CSS 圖層，**0 個 draw call** |
| 島民與小船 | 同造型收成 1 個 InstancedMesh，動畫只改矩陣 |
| 渲染策略 | **按需渲染**：沒有輸入、沒有狀態變化就不呼叫 render，連 RAF 都不排程 |
| 故事畫面 | 開啟時 `scene.pause()`，地圖完全停止渲染；關閉時 `resume()` |
| 像素比 | 依裝置分級設上限：低階手機 1.0 ／一般手機 1.5 ／桌機 2.0 |
| 抗鋸齒 | 手機關閉，桌機開啟 |
| 更新頻率 | 有動畫時低階手機 24fps、其他 36fps；靜止時按需渲染，多數時間是 0fps |
| 霧與遠裁切面 | 隨鏡頭距離調整，拉遠時遠處的島不會被整片霧吃掉 |

### 實測數字

用 Playwright ＋ Chromium 實測，390×844（iPhone 尺寸）與 1280×800：

| 場景 | Draw calls | Triangles | 貼圖 |
|---|---|---|---|
| 全新存檔（六島未解鎖） | 35 | 12,060 | 0 |
| 六島全開、18 條航線全部長出（七種氣候區） | 51 | 40,562 | 0 |
| 同上，雨天（多 80 根雨絲） | 52 | 40,522 | 0 |

預算上限設在 60 draw calls（`src/world/perf.js` 的 `BUDGET`），目前用掉 51。
執行中可以用 `window.__tti.scene.stats()` 查當下的數字。

地面細節讓 draw calls 從 40 爬到 48（八種新道具型別），氣候區再加三種到 51。
三角形那邊完全不用擔心，draw calls 那邊**只剩 7 種型別的空間**。

> `BUDGET` 原本只是寫在 `perf.js` 裡沒人檢查的數字，所以它從 40 爬到 48 都沒人發現。
> 現在 `tools/world-budget.mjs` 會在 `npm test` 時擋下來——它用
> 「道具型別 ＋ 島民型別 ＋ 地形 ＋ 固定開銷」估算，刻意估得比實際高一點
> （目前估 50、實測 48），寧可早一步擋住。要加超過十種新道具，就得先合併型別
> 或重新檢討 `BUDGET`，不要偷偷超過。

**「細節多」不是 3D 網頁跑不動的原因。** 真正的成本是 draw call 數、貼圖記憶體、
即時陰影／後製，以及有沒有一直重繪——三角形數量反而最便宜。壓力測試裡額外塞進
5,000 個用 instancing 畫的裝飾物（＋40 萬個三角形），draw call 只增加 1，
每幀成本量不出差別。所以要加細節，規則只有兩條：

1. 同一種東西用 instancing 一次畫完。
2. 不要為了細節引進貼圖檔、即時陰影或粒子。

會踩到上限的是「每個物件都長得不一樣」——一百種不同的小物件就是一百個 draw call。
地面細節就是踩在這條線上：鋪了 603 個實例只花八個 draw call，因為它們只有八種。

## 氣候區

每座島屬於一個**氣候區**（`biomes`），決定它的地表配色、植被與地面細節。
加一個新氣候區＝在 `island_map.json` 的 `biomes` 裡多一筆，不用改任何程式。

| 島 | 氣候區 | 為什麼是這一個 |
|---|---|---|
| 透中島（主島）・願望島 | 綠洲 | 中午十二點的島：有水、有樹、最暖的那一塊 |
| 01 界線島 | 沙漠 | 地平線很清楚，一眼看得到邊界在哪裡 |
| 02 回聲島 | 花季 | 粉色、柔軟 |
| 03 夜哨島 | 針葉林 | 天黑得早，樹站得很直 |
| 04 署名島 | 高原 | 風很大，但看得很遠 |
| 05 歸返島 | 珊瑚海 | 水很淺，踩得到底 |
| 06 歇腳島 | 草原 | 可以直接躺下來的那種地方 |

一個氣候區可以寫三件事，**都是選填**，沒寫就沿用全域設定：

```jsonc
"desert": {
  "name": "沙漠", "line": "地平線很清楚。",
  "flora": "desert",                 // 用哪一張植被表
  "surfaces": {                      // 覆寫地表配色，沒寫到的沿用 SURFACE_COLORS
    "sand": { "top": "#f4e2b0", "side": "#dcb87a" }, …
  },
  "clutter": {                       // 覆寫地面細節，沒寫到的沿用 ground_clutter
    "sand": { "count": 10, "types": ["pebble", "pebble", "desert_shrub", "shell"] }, …
  }
}
```

氣候區只新增了三種道具（仙人掌、旱生灌木、珊瑚扇），所以代價是固定的三個 draw call，
**不隨島數增加**——第七個氣候區如果沿用現有道具，就是零成本。

一個踩過的坑：`coral_fan` 原本同時放進植被表與地面細節，結果在植被的位置會被
放大成一把粉紅色的大傘。地面細節的尺寸是貼地的那一階，不能直接拿去當樹。

## 地圖內容由資料產生

整個 3D 場景從 `content/island_map.json` 生成，程式裡沒有寫死任何一座島：

```jsonc
{
  "hex": { "size": 1.0, "orientation": "flat-top", "level_height": 0.42, "base_depth": 0.55 },
  "home": { "hexes": [...], "landmarks": [...], "interactions": [...], "animals": [...] },
  "wish_island": {                          // 碼頭許願的另一半
    "hexes": [...], "landmarks": [...],
    "dock_slots": [...],                    // 小船停靠位，放幾艘就佔幾個
    "tree_slots": [...]                     // 每個主題一個位子，照公司回應長樹
  },
  "islands": [{
    "island_id": "island_boundary",
    "origin": { "q": -5, "r": 2 },        // 軸向座標，加到各 hex 之上
    "base":   { "hexes": [...], "landmarks": [...] },
    "growth": [{ "growth_id": "...", "route_id": "...", "hexes": [...], "landmarks": [...] }]
  }],
  "flora_table": { ... },                  // 各島的樹種
  "flora_density": { ... }                 // 每種植被的密度
}
```

- 座標是 flat-top 軸向座標：`x = size × 1.5 × q`、`z = size × √3 × (r + q/2)`。
- 草木不寫在資料裡，由 `islandBuilder.js` 以「島嶼 id ＋ 已解鎖航線數」為種子的亂數散佈，
  所以同一座島每次重建長出來的位置都一樣，但資料檔不用塞幾百筆座標。
- 新增一座島＝在 `islands[]` 多一筆，不用改任何程式。

## 走進島裡

群島總覽回答「我有幾座島」，走進去才回答「這座島上發生過什麼」。
兩層用的是**不同的一套幾何**：

| | 群島總覽 | 島嶼內部 |
|---|---|---|
| 地形 | 六角地塊（`hexGeometry.js`） | 自由多邊形（`landmass.js`） |
| 繪製 | 有動作才畫（on-demand） | 持續畫，依機型 24／30／36 fps |
| 載入 | 一開始就有 | 點進去才下載 |
| 典型用量 | 51 draw call ／ 40,562 三角形 | 40 draw call ／ 14,304 三角形 |

六角格排不出「不對稱的島、左後兩層砂岩、底部大岩向下收尖」這種輪廓，
所以島內改用自由多邊形：一片頂面，加上往下往內收的裙邊。
一座島不管分幾層都合併成一個幾何，只佔一個 draw call。

### 檔案

```
content/islands/01_sand_oasis.json   一座島的全部內容（地形／鋪面／道具／居民）
src/world/landmass.js                自由多邊形地形
src/world/islandScene.js             島內場景引擎（相機、動畫、點選）
src/world/islandProps/sandOasis.js   這座島專屬的道具
src/core/islandScenes.js             依島嶼 id 動態載入，沒進去就不下載
```

道具的幾何輔助（`box`／`cyl`／`face`／`merge`…）統一放在 `src/world/shapes.js`，
群島與島內共用，所以兩層的動物與家具長得像同一個世界的東西。

### 兩個踩過的坑

**多邊形繞向。** 三角形的正面由頂點繞向決定。外框順時針或逆時針寫起來都很自然，
但繞反了整片就朝下，背面剔除之後從上面看會整個消失——三條小徑就這樣不見過一次。
現在 `slab()` 與 `layer()` 進來先統一繞向。

**離開島嶼要收乾淨。** `dispose()` 原本靠材質判斷該釋放哪些幾何，
地形與鋪面那兩個合併 mesh 用的是共用材質、又不是 InstancedMesh，
剛好從判斷式中間漏掉，每進出一次留下兩個幾何。
現在一律走訪整棵場景樹逐一釋放，進出五次幾何數維持不變。

## 可及性

- 名牌與互動點是真的 `<button>`，可用鍵盤聚焦、有 `aria-label`。
- 尊重 `prefers-reduced-motion`：關閉所有進場動畫與標籤過場。
- 文字與背景對比度依循 WCAG AA；選項按鈕最小觸控區域 44×44。
- WebGL 無法初始化時顯示明確的說明，而不是白畫面。
